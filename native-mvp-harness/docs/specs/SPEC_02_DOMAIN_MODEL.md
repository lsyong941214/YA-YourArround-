# DOMAIN_MODEL — 용어, 역할, 상태 전이

기존 웹에서 검증된 서비스 흐름을 네이티브 MVP 기준으로 정리한 문서다. 코드 이름·API enum·사용자 문구가 이 표를 따른다.
표시 `[정책 확인]`은 결정서 11장 "착수 전 팀 확인사항"에 해당해 팀 결정이 필요한 항목이다.

## 1. 용어

| 사용자 문구 | 코드/API 이름 | 설명 |
|---|---|---|
| 주민 | `resident` | 소개를 받는 일반 사용자 |
| 이장님 | `chief` | 초대코드로 주민을 모으고 주민끼리 소개(중개)하는 사용자 |
| 초대코드 | `invite_code` | 이장이 발급하는 1회용 코드. 주민↔이장 관계를 만드는 **유일한 경로** |
| 이장 연결 | `chief_link` | 주민과 이장의 관계 |
| 매칭 신청 | `match_request` | 주민이 이장에게 특정 주민을 소개해 달라고 요청 |
| 주변인 테스트 | `blind_test` | 두 주민이 밸런스 게임으로 취향을 비교하는 테스트 |
| 문항 세트 | `question_set` | 게시된 문항 묶음(버전 고정) |
| 결과서 | `blind_test_result` | 점수·등급·선택 비교 |
| 대화방 | `chat_room` | 매칭 성사 후 두 주민의 1:1 채팅 |
| 이장 리뷰 | `chief_review` | 매칭 성사 후 이장에 대한 평점·후기 |
| 신고 / 차단 | `report` / `block` | 안전 기능 |
| 이용 제한 | `restriction` | 정지·영구 정지 |

## 2. 역할

- 한 계정의 역할은 `resident` 또는 `chief`.
- 기존 웹은 홈에서 역할을 자유롭게 토글했고, 이 때문에 자기매칭·역할 불일치 데이터가 생겼다.
  MVP는 **역할 변경을 서버 API로만** 허용하고, 진행 중인 매칭·테스트가 있으면 거절한다. 변경 허용 여부·횟수는 `[정책 확인]`.
- 운영자 역할은 사용자 역할과 별개인 서버 관리 역할(`admin_roles`)이다. `profiles`의 플래그로 두지 않는다.

## 3. 프로필

- 필수: 프로필 사진, 이름(표시명), 역할, 생년월일, MBTI / 선택: 직업, 지역, 소개.
- **만 19세 미만 가입 불가** — 서버(DB 트리거 또는 API)에서 검증.
- 지역은 시·구 단위 짧은 텍스트(상세 주소 금지). 정밀 위치 수집 안 함.
- 사진: 초기 기준 최대 3장, 장당 1MB 이하(리사이즈·압축·EXIF 제거 후 업로드). 서버에서 형식·용량·소유권 재검사.
- 사진이 없을 때 표시: 이름 첫 글자 + 사용자별 고정 톤 색(`docs/specs/SPEC_06_DESIGN_SYSTEM.md` 아바타).
- 공개 프로필 범위(누가 무엇을 보는지)는 `[정책 확인]`. 기본안: 같은 이장에 연결된 주민과 매칭 당사자만.

## 4. 초대와 이장 관계

```
이장: 코드 발급(1회용) ──▶ 주민: 코드 입력 ──▶ [DB 함수] 코드 사용 처리 + chief_link 생성 (한 트랜잭션)
```
- 코드 보유 = 이장의 승인. 별도 수락 단계 없음.
- 이미 사용·폐기·만료된 코드, 자기 자신이 발급한 코드, 차단 관계, 정지 계정은 거절.
- 동시에 같은 코드로 두 요청이 와도 **한 번만 성공** (DB 유일 제약/행 잠금으로 보장, 테스트 필수).

## 5. 매칭 신청 상태

| API 값 | 기존 웹 코드 | 의미 | 다음 상태 |
|---|---|---|---|
| `pending_chief` | `pend` | 이장 검토 대기 | `chief_accepted`, `chief_rejected`, `canceled` |
| `chief_accepted` | `c_acpt` | 이장이 소개 → 대상 주민 응답 대기 | `matched`, `resident_rejected`, `canceled` |
| `chief_rejected` | `c_rjct` | 이장 거절(종료) | — |
| `matched` | `r_acpt` | 대상 주민 수락 = **매칭 성사**, 대화방 생성 | — |
| `resident_rejected` | `r_rjct` | 대상 주민 거절(종료) | — |
| `canceled` | (신규) | 신청자 취소 또는 차단·정지로 서버가 종료 | — |

규칙:
- 신청자 ≠ 대상 주민. 신청자·대상은 `resident`, 중개자는 `chief`이며 둘 다 그 이장과 연결돼 있어야 한다.
- 전이는 **해당 역할의 당사자만** 가능: 이장만 `pending_chief → chief_*`, 대상 주민만 `chief_accepted → matched/resident_rejected`.
- `matched` 전이는 DB 함수 한 번으로: 상태 변경 + 대화방 생성 + 알림 outbox 기록.
- 신청 한도(기존 웹 "남은 매칭 횟수" 5회)는 서버 설정값. 한도 초과는 서버가 거절한다.
- 매칭 성사 후 신청자는 이장 리뷰(1~5점 + 짧은 후기)를 매칭당 1회 남길 수 있다.

## 6. 주변인 테스트

### 상태

| API 값 | 기존 웹 코드 | 의미 |
|---|---|---|
| `pending` | `pend` | 대상 주민 응답 대기 |
| `in_progress` | `acpt` | 수락 → 양쪽 게임 진행/결과 행동 대기 |
| `ended` | `rjct` | 거절, 진행 중 종료, 또는 결과서에서 한쪽이 종료 |
| `completed` | `done` | 결과서에서 연결 확정 |

### 진행

1. 신청 시 서버가 게시된 최신 문항 세트에서 문항을 뽑아 **문항 세트 버전 + 계산 규칙 버전 + 문항 순서**를 고정 저장한다. 이후 문항이 바뀌어도 진행 중 테스트는 영향 없음.
   - 기존 웹 기준: 카테고리 일상/음식/여행지에서 3/3/4개, 총 10문항. 개수·비율은 서버 설정(1~20문항 범위).
2. 각자 문항마다 A/B 중 하나 선택. 선택은 즉시 서버 저장(중복 방지 키), 앱 종료 후 이어하기 가능.
3. 양쪽 모두 끝나면 **서버가 점수 계산** → 결과서.

### 점수(기존 웹 규칙 = 계산 규칙 v1)

- MBTI 궁합 점수(50~100): 기본 50, E/I가 다르면 +14, N/S가 같으면 +25, J/P가 다르면 +11 (T/F 무관).
- 선택 일치 점수: 같은 선택 문항 수 ÷ 전체 문항 수 × 100.
- 결과 점수 = MBTI 궁합 × 0.5 + 선택 일치 × 0.5 (100점 만점).
- 등급: ≤20 `opposite` · ≤50 `check` · ≤70 `ok` · ≤90 `good` · 그 이상 `best`. 등급별 안내 문구는 서버 콘텐츠.

### 결과서 행동

| 행동 | API 값 | 기존 웹 |
|---|---|---|
| 연락하기 | `contact` | `ctct` |
| 이장님 확인요청 | `ask_chief` | `rvw` (등급 `check`에서만 제공) |
| 종료하기 | `end` | `end` (등급 `good`/`best`에서는 미제공) |

- 한쪽이라도 `end` → `ended`, 이미 이장에게 간 확인요청은 취소.
- 첫 `ask_chief` → 이장에게 매칭 신청 1건 생성(`pending_chief`). 둘 다 `ask_chief` → 이장 거치지 않고 `matched`.
- 둘 다 `contact` → `completed` + 매칭 `matched`(대화방 생성).
- 모든 전이는 DB 함수 하나에서 처리하고, 상대방 화면은 Realtime 신호 → API 재조회로 갱신.

## 7. 채팅

- `matched` 매칭의 두 주민만 대화방 조회·전송 가능. **이장은 볼 수 없다.**
- 메시지 원본은 DB. 1~2000자. 클라이언트가 만든 `client_message_id`로 중복 방지. 상태: 전송 중 / 완료 / 실패(사용자 재시도).
- 재연결·앱 복귀 시 마지막 메시지 이후를 API로 다시 조회한다.
- 차단 또는 이용 제한이 생기면 대화방은 **읽기 전용**(전송 거절)으로 바뀐다.
- 금칙어(불법 광고·조건만남 등)는 서버에서 검사, 목록은 관리자 설정. 걸리면 전송 거절 + 안내.
- 푸시 문구에 메시지 원문을 넣지 않는다("새 메시지가 도착했어요").

## 8. 신고·차단·이용 제한

- 신고: 대상 사용자 + 사유(허위 프로필·도용 사진, 불법 광고, 욕설·괴롭힘, 기타) + 상세 + 선택적 증거(해당 메시지 ID).
- 신고는 **검토 대기열**로 간다. 신고 건수만으로 영구 정지를 자동 확정하지 않는다. 자동 조치를 둔다면 임시 제한 + 우선 검토까지만 `[정책 확인]`.
- 차단은 **양방향 효과**: 서로의 프로필·추천·신청·테스트 대상에서 사라지고 대화방은 읽기 전용.
- 이용 제한 상태: `active` · `suspended`(기간) · `banned`. 모든 업무 API·조회·Realtime 구독에서 현재 상태를 확인(기존 JWT만 믿지 않음). 제한 계정은 `account.restricted` 화면.
- 탈퇴: 앱 설정 + 공개 웹 요청 경로. 재인증 필요. 보관·삭제 범위는 `[정책 확인]`.

## 9. 운영 지표 퍼널

가입 → 프로필 완료 → 초대 연결 → 매칭 수락 → 테스트 완료 → 첫 대화 → 첫 답장. 각 단계 이벤트를 서버에서 기록·집계한다.
