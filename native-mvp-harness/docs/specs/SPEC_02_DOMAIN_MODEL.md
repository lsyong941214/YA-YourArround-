기존 웹에서 검증된 흐름을 바탕으로, 2026-09-30 추가 요구사항(번호 확인 초대코드, 이장 네트워크, 매칭 대기열,
프로필 공개 동의, 가입 정보 상세화)을 반영한 도메인 규칙이다. 코드 이름·API enum·사용자 문구가 이 문서를 따른다.

- `[정책 확인]`: 결정서 11장 "착수 전 팀 확인사항"에 해당해 팀 결정이 필요한 항목
- `(임시 이름)`: 기획에서 이름을 나중에 바꾸기로 한 항목. 코드 식별자는 이 문서의 영어 이름을 쓰고, 이름이 바뀌면 사용자 문구만 바꾼다

## 1. 용어

| 사용자 문구 | 코드/API 이름 | 설명 |
|---|---|---|
| 주민 | `resident` | 소개를 받는 사용자. **소속 이장은 1명**(N:1) |
| 이장님 | `chief` | 주민을 초대·관리하고, 다른 이장과 연결해 주민을 소개하는 사용자 |
| 내 이장님 | `home_chief` | 주민 입장에서 자신이 소속된 이장 |
| 초대코드 | `invite` | 휴대폰 번호 확인이 붙은 1회용 코드(4절) |
| 이장 연결 | `chief_link` | 이장↔이장 관계(N:M, 양방향) |
| 소개 요청 | `intro_request` | 주민이 내 이장님에게 "소개받고 싶어요"를 보내는 것 |
| 매칭 대기열 `(임시 이름)` | `match_queue` | 이장이 소개할 주민을 올려두는 목록. 연결된 이장들이 탐색 |
| 대기열 올리기 `(임시 이름)` | `queue_entry` | 대기열에 올라간 주민 1명의 항목 |

| 열람 요청 / 열람 허락 | `profile_view_request` / `profile_view_grant` | 다른 이장이 내 프로필을 보기 위한 요청과 그 허락 |
| 주변인 테스트 | `blind_test` | 두 주민이 밸런스 게임으로 취향을 비교하는 테스트 |

| 이장 리뷰 | `chief_review` | 매칭 성사 후 이장에 대한 평점·후기 |
| 신고 / 차단 / 이용 제한 | `report` / `block` / `restriction` | 안전 기능 |

## 2. 역할과 관계 구조

```
   [이장 A] ════ 이장 연결(N:M) ════ [이장 B] ════ [이장 C]
    │  │                              │
  주민1 주민2  (주민↔이장 N:1)        주민3
```

- 한 계정의 역할은 `resident` 또는 `chief`.
- 주민은 **이장 1명에게만** 소속된다. 소속 변경은 `[정책 확인]`(기본안: 탈퇴 후 재초대만 허용).
- 이장끼리는 여러 명과 연결될 수 있다. 연결은 **양쪽 모두 같은 권한**(방향 없음).
- 역할 변경은 서버 API로만, 진행 중인 제안·테스트가 있으면 거절. 변경 허용 여부는 `[정책 확인]`.
- 운영자 역할은 별도 서버 관리 역할(`admin_roles`). `profiles` 플래그로 두지 않는다.

## 3. 가입과 온보딩 흐름

```
앱 첫 실행 → [앱 소개 온보딩](첫 실행 1회) → 로그인 선택
  → 약관 동의
  → 초대코드 + 본인 휴대폰 번호 입력 (4절 확인)
      ├ 주민 초대코드 → 역할 = 주민 고정 → [주민 역할 안내] → 프로필 작성 → [프로필 공개 설정 선택](6절) → 홈
      └ 이장 초대코드 → 역할 = 이장 고정 → [이장 역할 안내] → 프로필 작성 → 홈
  (초대코드 없이 시작) → [역할 안내: 주민/이장 비교] → 이장만 가입 가능, 주민은 초대코드 입력 안내
```

- **주민은 초대코드 없이 가입할 수 없다.** 이장 가입을 초대 없이 열어둘지, 관리자 승인제로 할지는 `[정책 확인]`(기본안: 열어두고 원격 설정으로 승인제 전환 가능).
- 역할 안내는 역할을 **고르기 전에**, 또는 초대코드로 역할이 정해진 직후에 보여준다(두 역할의 차이를 이해한 뒤 진행).
- 온보딩 문구·이미지는 서버 콘텐츠로 바꿀 수 있고, 앱에 기본본을 내장한다(`SPEC_01` 5절).
- 설정·FAQ에서 "앱 소개 다시 보기", "역할 안내 다시 보기"를 제공한다.

## 4. 초대코드 (휴대폰 번호 확인)

목적: **초대한 사람이 입력한 번호와 가입자 본인 번호가 일치할 때만** 코드를 쓸 수 있게 해 남용을 막는다.
번호 원문은 저장하지 않는다.

### 종류

| `invite_type` | 발급자 | 사용 결과 |
|---|---|---|
| `resident` | 이장 | 새 사용자가 **주민으로 가입** + 발급 이장에게 소속 |
| `chief_link` | 이장 | 새 사용자는 **이장으로 가입** + 발급 이장과 연결 / 이미 이장이면 **연결만** 생성 |

### 발급 (다건 가능)

1. 이장이 번호를 직접 입력하거나 **기기 연락처에서 여러 명을 선택**한다(선택한 연락처의 번호만 사용, 주소록 전체 업로드 금지).
2. 앱이 번호 목록을 서버로 보낸다. 서버는 번호별로:
   - 번호 정규화(국제 형식 `+8210…`) → 형식 검증
   - `code` = 무작위 8자리(혼동 문자 제외 영숫자)
   - `phone_check` = `HMAC-SHA256(서버 비밀키[key_version], 정규화 번호 + code)`
   - 저장: `code`, `phone_check`, `key_version`, `invite_type`, 발급 이장, 만료시각, 상태. **번호 원문은 저장·로그 금지**
3. 응답으로 번호별 `code`를 받은 앱이 OS 문자 앱/공유 시트를 열어 이장이 직접 보낸다(서버 문자 발송 없음 → 비용 0).
   - 번호는 앱 메모리에서만 쓰고, 문자 작성 화면을 연 뒤 버린다.

### 사용

1. 가입자가 `code` + **본인 휴대폰 번호**를 입력한다.
2. 서버: 코드 상태·만료 확인 → `HMAC(비밀키[key_version], 입력 번호 정규화 + code) == phone_check` 비교(상수 시간 비교).
3. 일치하면 한 트랜잭션으로 **코드 사용 처리 + 가입/소속 또는 이장 연결 생성**. 가입자 번호도 저장하지 않는다.

### 규칙

- 코드 상태: `active` → `used` / `revoked`(이장 폐기) / `expired`(기본 7일, 원격 설정) / `locked`(번호 불일치 5회, 원격 설정).
- 번호 불일치는 코드 존재 여부와 같은 오류로 응답(`invite_invalid`) — 번호 추측 단서를 주지 않는다.
- 같은 코드로 동시에 두 요청이 와도 **한 번만 성공**(행 잠금, 테스트 필수).
- 다건 발급 한도: 1회 최대 20건, 이장당 미사용 코드 최대 50개(원격 설정).
- 자기 자신에게 발급한 코드, 차단 관계, 이용 제한 계정은 거절.
- 비밀키는 Edge Function secret에만 두고 `key_version`으로 교체한다(교체 후에도 이전 키로 발급된 코드는 만료 전까지 검증).
- **한계:** 가입자가 번호를 직접 입력하므로 "번호 소유"까지 증명하지는 않는다(단순 남용 방지). 소유 확인이 필요해지면 SMS 인증·카카오 전화번호 동의를 같은 구조에 추가한다 `[정책 확인]`.
- 법적 성격: 번호가 서버를 잠깐 거치고, `phone_check`는 비밀키와 결합하면 번호와 연결될 수 있어 가명정보로 볼 여지가 있다. 이장에게 "입력한 번호는 저장되지 않고 확인용으로만 쓰여요"를 안내하고, 법무 검토를 받는다 `[정책 확인]`.

## 5. 이장 연결과 매칭 대기열

### 이장 연결 (`chief_link`)

- 생성: `chief_link` 초대코드 사용(4절)으로만. 연결되면 양쪽 모두 상대 이장의 대기열·주민 목록을 탐색할 수 있다.
- 해제: 어느 쪽이든 즉시 해제 가능. 해제 시 상대 쪽 **열람 허락 전부 만료**, 진행 중 제안 중 두 이장이 관여한 건은 `canceled`.
- 이장 간 차단은 연결 해제 + 재연결 불가.

### 소개 요청 → 대기열

```
주민: "소개받고 싶어요"(intro_request, 선호 메모 선택)
  → 내 이장님: 확인 ─┬ 대기열에 올리기 → queue_entry(waiting)
                     └ 보류/거절(사유 선택) → 주민에게 알림
이장이 주민 요청 없이 직접 올릴 수도 있다 → 주민에게 알림 + 주민이 내리기 가능
```

| `queue_entry.status` | 의미 |
|---|---|
| `waiting` | 대기열에서 탐색 가능 |
| `proposing` | 소개 제안이 진행 중(동시에 1건, 원격 설정) — 탐색 목록에서 "진행 중" 표시 |
| `matched` | 매칭 성사로 내려감 |
| `withdrawn` | 주민 또는 내 이장님이 내림 |
| `expired` | 기본 30일 경과(원격 설정). 이장이 다시 올릴 수 있음 |

- 주민 1명은 동시에 대기열 항목 1개.
- 대기열에 올리려면 프로필이 완성돼 있어야 한다(4개 필수 항목 + 사진).

### 탐색 (다른 이장의 주민 보기)

- 연결된 이장의 **대기열을 먼저** 보여준다(최신순, 내 주민과 조건이 맞는 순 정렬은 후속).
- 대기열이 비었거나 더 보고 싶으면 **상대 이장 프로필 → 소속 주민 목록**으로 탐색한다.
- 탐색 목록에는 주민의 **요약 카드**만 나온다. 전체 프로필은 6절의 공개 설정에 따라 열린다.
- 조회 한도: 이장당 하루 전체 프로필 열람·요청 50건(원격 설정) — 주민 정보 대량 수집 방지.

## 6. 프로필 공개 설정 (주민 가입 시 필수 선택)

다른 이장이 내 프로필을 보려고 할 때의 처리 방식을 **주민이 가입 시 직접 고른다.** 미리 선택된 기본값은 두지 않는다. 설정에서 언제든 바꿀 수 있다.

| 값 | 화면 문구(제목 / 설명) | 동작 |
|---|---|---|
| `open` | **바로 보여줘도 괜찮아요** / 연결된 이장님이라면 따로 묻지 않고 내 프로필을 볼 수 있어요. | 요청 없이 즉시 열람 |
| `home_chief_approval` | **내 이장님이 확인하고 보여주세요** / 내 이장님이 괜찮다고 하면 프로필이 공개돼요. | 요청 → 내 이장님 허락 |
| `self_approval` | **제가 직접 확인할게요** / 보고 싶다는 요청이 오면 알려드려요. 제가 허락해야 공개돼요. | 요청 → 주민 본인 허락 |

화면 제목과 안내(정확한 문구는 `SPEC_06` 5-2절 `ConsentChoice`):
> **다른 이장님이 내 프로필을 보고 싶어 하면 어떻게 할까요?**
> 내 이장님과 연결된 이장님들은 소개할 이웃을 찾을 때 프로필을 볼 수 있어요. 허락 전에는 나이·키·사는 지역만 보여요.

### 열람 요청과 허락

- 요청: 다른 이장이 "프로필 보기 요청" → `profile_view_request(pending)` → 설정에 따라 내 이장님 또는 주민 본인에게 알림.
- 응답: `approved` → `profile_view_grant` 생성(유효 30일, 원격 설정) / `declined` / 7일 무응답 `expired`.
- 거절 후 같은 이장의 재요청은 30일 뒤부터.
- 열람 가능 판단은 **요청 시점마다 서버가** 한다: 이장 연결 유지 + 주민 설정이 `open`이거나 유효한 `grant` 존재 + 차단·이용 제한 없음.
- 주민이 설정을 **더 엄격하게** 바꾸면(`open` → 승인제, `home_chief_approval` → `self_approval`) 기존 허락은 즉시 만료.
- 주민은 "내 프로필을 본 이장님" 목록(누가, 언제)을 볼 수 있다.

### 공개 범위

| 보는 사람 | 요약 카드 | 전체 프로필 |
|---|---|---|
| 내 이장님 | ✅ | ✅ |
| 연결된 다른 이장(허락 전) | ✅ 나이·키·거주지(시군구) | ❌ |
| 연결된 다른 이장(허락 후 / `open`) | ✅ | ✅ |
| 연결 안 된 이장 | ❌ | ❌ |
| 소개 제안을 받은 상대 주민 | ✅ | ✅(제안 기간 동안) |

- 요약 카드에 사진을 흐리게라도 넣을지는 `[정책 확인]`(기본안: 넣지 않음).
- ②와 ③을 합친 "나 또는 내 이장님 중 누구든 허락" 선택지가 필요한지 `[정책 확인]`.

## 7. 소개 제안 (`match_proposal`)

이장이 주민 두 명을 잇는다. 두 주민이 **같은 이장 소속**이면 3단계를 건너뛴다.

```
① 제안 이장: 내 주민 A + 상대 주민 B 선택, 방식 선택(바로 연결 / 주변인 테스트 먼저), 추천 메모
② (B가 다른 이장 소속이면) 상대 이장 동의
③ 두 주민에게 상대 프로필과 함께 제안 도착 → 각자 수락/거절
④ 둘 다 수락 → 바로 연결: matched + 대화방 / 테스트 먼저: 주변인 테스트 시작(8절)
```

- 제안은 **양방향**으로 시작할 수 있다: 이장 A가 이장 B의 대기열에서 B 소속 주민을 찾아 제안할 수도 있고, 이장 B가 이장 A의 대기열에서 A 소속 주민을 찾아 제안할 수도 있다.
- 제안 대상 주민이 승인제 공개 설정이면 **열람 허락을 먼저** 받아야 제안할 수 있다.

| `status` | 의미 | 다음 |
|---|---|---|
| `pending_chief` | 상대 이장 동의 대기(다른 이장 소속일 때만) | `pending_residents`, `chief_declined`, `canceled` |
| `pending_residents` | 두 주민 응답 대기 | `matched`, `testing`, `resident_declined`, `expired`, `canceled` |
| `testing` | 주변인 테스트 진행 중 | `matched`, `ended` |
| `matched` | 매칭 성사, 대화방 생성 | — |
| `chief_declined` / `resident_declined` | 상대 이장 / 주민 한 명이라도 거절 | — |
| `ended` | 테스트 결과에서 종료 | — |
| `expired` | 응답 기한(기본 72시간) 경과 | — |
| `canceled` | 제안 이장 취소, 연결 해제, 차단·이용 제한으로 서버가 종료 | — |

규칙:
- 제안이 `pending_*`/`testing`이면 관련 `queue_entry`는 `proposing`, 종료되면 `waiting`으로 복귀, `matched`면 `matched`.
- 전이는 해당 당사자만: 상대 이장만 ②, 각 주민은 자기 응답만.
- `matched` 전이는 DB 함수 하나: 제안 상태 + 대기열 항목 + 대화방 생성 + 알림 outbox.
- 거절 사유는 주민 선택(말하지 않음 포함). 상대 주민에게는 사유를 보여주지 않는다.
- 이장당 동시 진행 제안 수 한도(원격 설정).
- 매칭 성사 후 두 주민은 각자 **내 이장님**과 (다르면) 상대 이장에게 리뷰를 남길 수 있다 `[정책 확인]`.

**기존 결정에서 바뀐 점:** 기존 웹의 "주민이 특정 주민을 지정해 이장에게 신청(`match_request`)" 흐름은 **소개 요청 → 대기열 → 이장 제안**으로 대체한다.

## 8. 주변인 테스트

제안 방식이 "주변인 테스트 먼저"이고 두 주민이 수락하면 시작한다.

1. 시작 시 서버가 게시된 최신 문항 세트에서 문항을 뽑아 **문항 세트 버전 + 계산 규칙 버전 + 문항 순서**를 고정 저장한다.
   - 기존 웹 기준 카테고리 일상/음식/여행지 3/3/4개, 총 10문항. 개수·비율은 서버 설정(1~20문항).
2. 각자 A/B 선택 → 즉시 서버 저장(중복 방지 키), 앱 종료 후 이어하기.
3. 둘 다 끝나면 **서버가 점수 계산** → 결과서.

점수(계산 규칙 v1, 기존 웹과 동일):
- MBTI 궁합(50~100): 기본 50, E/I 다르면 +14, N/S 같으면 +25, J/P 다르면 +11.
- 선택 일치: 같은 선택 수 ÷ 문항 수 × 100.
- 결과 = 궁합 × 0.5 + 일치 × 0.5. 등급: ≤20 `opposite` · ≤50 `check` · ≤70 `ok` · ≤90 `good` · 그 이상 `best`. 등급 문구는 서버 콘텐츠.

결과서 행동: `contact`(연락하기) / `end`(종료하기).
- 둘 다 `contact` → 제안 `matched` + 대화방. 한쪽이라도 `end` → 제안 `ended`.
- 기존 웹의 `ask_chief`(이장님 확인요청)는 이미 이장이 제안한 구조라 제외했다. 다시 필요하면 `[정책 확인]`.

## 9. 프로필

| 항목 | 필수 | 입력 방식 | 저장 | 프로필 카드 |
|---|---|---|---|---|
| 사진 | ✅ 1~3장 | 촬영/앨범, 리사이즈·압축·EXIF 제거 | Storage private | ✅ 대표 사진 |
| 표시 이름 | ✅ | 텍스트 2~10자 | | 전체 프로필 |
| 생년월일 | ✅ | 날짜 선택 | `birth_date` — **노출 안 함** | ✅ **만 나이**로 표시 |
| 키 | ✅ `[정책 확인]` | 숫자 선택 140~210cm | `height_cm` smallint | ✅ |
| 직업(회사명) | ✅ | 회사명 검색 후 선택, 없으면 직접 입력 | `company_id` 또는 `company_name_input` | ✅ |
| 사는 지역 | ✅ | **시/군/구 검색 후 선택**(자유 입력 불가) | `region_code`(행정구역 시군구 코드) + `region_name` | ✅ "서울 마포구" |
| MBTI | ✅ | 16개 중 선택 | | 전체 프로필 |
| 소개 | 선택 | 텍스트 ≤300자, 금칙어 검사 | | 전체 프로필 |

- **만 19세 미만 가입 불가** — 서버에서 검증.
- **회사명:** 서버의 회사 목록(`companies`)에서 검색·선택. 없으면 직접 입력 → 새 이름은 관리자 검토 후 목록에 합류(표기 통일). 회사 인증(회사 이메일 등)은 MVP 제외. 회사명을 누구에게까지 보일지는 `[정책 확인]`(기본안: 요약 카드부터 표시).
- **지역:** 주소 전체가 아니라 **시군구 목록에서 검색**한다(예: "마포" → 서울특별시 마포구). 목록은 서버가 제공하고 행정구역 변경 시 서버에서 갱신한다. 상세 주소·좌표는 받지도 저장하지도 않는다. 도로명주소 검색 API를 쓰더라도 시군구만 추출하고 나머지는 버린다.
- 사진이 없을 때 표시(오류 대비): 이름 첫 글자 + 사용자별 고정 톤 색.

## 10. 채팅

- `matched` 제안의 두 주민만 대화방 조회·전송. **이장은 볼 수 없다.**
- 메시지 원본은 DB. 1~2000자. `client_message_id`로 중복 방지. 전송 중/완료/실패(재시도).
- 재연결·앱 복귀 시 마지막 메시지 이후를 API로 다시 조회.
- 차단·이용 제한이 생기면 대화방은 읽기 전용.
- 금칙어는 서버 검사(목록은 관리자 설정). 푸시에 원문을 넣지 않는다.

## 11. 신고·차단·이용 제한

- 신고: 대상 + 사유(허위 프로필·도용 사진, 불법 광고, 욕설·괴롭힘, 개인정보 무단 이용, 기타) + 상세 + 선택적 증거. 이장이 열람한 프로필 정보를 외부로 유출한 경우도 신고 대상.
- 신고는 **검토 대기열**로 간다. 건수만으로 영구 정지를 자동 확정하지 않는다(자동 조치는 임시 제한 + 우선 검토까지 `[정책 확인]`).
- 차단은 양방향 효과: 탐색·제안·열람 요청 대상에서 제외, 대화방 읽기 전용.
- 이용 제한 `active` · `suspended`(기간) · `banned` — 모든 API·조회·구독에서 현재 상태 확인.
- 탈퇴: 앱 설정 + 공개 웹 요청 경로, 재인증. 탈퇴 시 대기열·열람 허락·진행 중 제안 모두 종료.

## 12. 운영 지표 퍼널

가입 → 프로필 완료 → 초대 연결 → 소개 요청 → 대기열 등록 → 제안 → 두 주민 수락 → (테스트 완료) → 첫 대화 → 첫 답장.
이장 네트워크 지표: 이장 연결 수, 다른 이장 소속 주민과의 제안 비율, 열람 요청 승인률.
